# Den configuration reference

Den is configured entirely through **environment variables**. This page
lists every variable each part of Den reads, with its default.

- The **backend** (`den-server`) and the **migrate** job read a `.env` file in
  their working directory if one exists, then the real environment (which
  wins). Den's repository has a [`.env.example`](https://github.com/AGlElectronics/den/blob/main/.env.example)
  for running the backend outside Docker.
- The **frontend** settings are baked in when the web app is **built**, not
  read at run time. Change them and rebuild.
- The **operator** reads only the real environment.

## Where the settings live on Kubernetes

The manifests in `deploy/kubernetes/base/den/` load the variables from four
objects in the namespace `conservices-den`, through `envFrom`. Plain
settings go into **ConfigMaps**, passwords and keys into **Secrets**:

| Object | Kind | Used by | Holds |
| --- | --- | --- | --- |
| `den-config` | ConfigMap | `den-backend` | Everything in [Backend](#backend) that is not a secret. |
| `den-secrets` | Secret | `den-backend` and its `migrate` initContainer | `DATABASE_URL`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `KEYCLOAK_CLIENT_SECRET`, `OPERATOR_TOKEN`. |
| `den-operator-config` | ConfigMap | `den-operator` | Everything in [Operator](#operator) that is not a secret. |
| `den-operator-secrets` | Secret | `den-operator` | `OPERATOR_TOKEN`, `PG_ADMIN_URL`, `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`, `FILES_S3_ACCESS_KEY_ID`, `FILES_S3_SECRET_ACCESS_KEY`. |

The two ConfigMaps are generated by Kustomize in the base. The two Secrets
are **not**: your overlay supplies them, as plain Secrets in
`overlays/example/secrets.yaml` for a local trial, or as `ExternalSecret`s
from a secret manager everywhere else (see [Secrets](../../operations/secrets.md)).

You never edit the base. Change ConfigMap values in your **overlay** with
`behavior: merge`, which replaces only the keys you list:

```yaml
# deploy/kubernetes/overlays/<yours>/kustomization.yaml
configMapGenerator:
  - name: den-config
    namespace: conservices-den
    behavior: merge
    literals:
      - APP_BASE_URL=https://den.example.org
      - OIDC_ISSUER_URL=https://login.example.org/realms/conservices
      - CORS_ALLOWED_ORIGINS=https://den.example.org
```

Kustomize adds a hash to generated ConfigMap names, so every ConfigMap
change restarts the pods automatically when you `kubectl apply -k`. Secrets
have fixed names, so after changing a Secret restart the pods that use it:

```sh
kubectl rollout restart -n conservices-den deploy/den-backend deploy/den-operator
```

In the Docker Compose development stack, the same variables are set per
service under `environment:` (and `build.args` for the frontend).

!!! note "Empty means unset"
    For every variable below, an empty value counts as not set, so the
    default applies. Booleans accept `true`/`false`, `1`/`0` and similar; an
    unparseable value also falls back to the default. Durations use Go
    syntax such as `15s` or `1m`.

## Backend

The backend checks its configuration at start-up and refuses to start, with
a message listing every problem, if something required is missing.

### Server

| Variable | Default | Required | Description |
| --- | --- | --- | --- |
| `APP_ENV` | `development` | no | Environment name, logged at start-up. `development` switches to human-readable console logs; anything else logs JSON (one object per line). |
| `APP_BASE_URL` | `http://localhost:8090` | no | Den's public address. Used to build pairing URLs, returned to modules as `den_base_url`, and used for the logo and background addresses pushed into Keycloak. Set it to the address modules and browsers use for Den, for example `https://den.example.org`. |
| `HTTP_ADDR` | `:8090` | no | Address the API listens on. The Kubernetes manifests and the compose file set `:8080`. |
| `SHUTDOWN_TIMEOUT` | `15s` | no | How long to let running requests finish when stopping. |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:3001` | no | Comma-separated browser origins allowed to call the API from another origin. Not needed when the web app and the API share an address (the normal setup behind nginx). |

### Database

| Variable | Default | Required | Description |
| --- | --- | --- | --- |
| `DATABASE_URL` | none | **yes** | PostgreSQL connection URL for Den's own database, for example `postgres://den:…@postgres.conservices-data.svc.cluster.local:5432/den?sslmode=disable`. Also the only variable the migrate step needs. |

### File storage (S3)

Den stores branding assets in one S3-compatible bucket. These are required
even in development (MinIO fills the slot there). The bucket is created at
start-up if it does not exist.

| Variable | Default | Required | Description |
| --- | --- | --- | --- |
| `S3_ENDPOINT` | none | **yes** | S3 endpoint URL, for example `http://minio.conservices-data.svc.cluster.local:9000` or `https://s3.eu-central-1.amazonaws.com`. `https://` turns on TLS. |
| `S3_BUCKET` | none | **yes** | Den's bucket, for example `den-data`. |
| `S3_ACCESS_KEY_ID` | none | **yes** | Access key for the bucket. |
| `S3_SECRET_ACCESS_KEY` | none | **yes** | Secret key for the bucket. |
| `S3_REGION` | `us-east-1` | no | Region. |
| `S3_USE_PATH_STYLE` | `true` | no | `true` for path-style requests (MinIO and most self-hosted services); `false` lets the client choose, as some providers require virtual-host style. |
| `S3_PUBLIC_BASE_URL` | derived | no | Replaces the scheme and host of presigned links when the browser cannot reach the internal storage address. When unset, a host containing `minio` is rewritten to `localhost`. Branding assets are always streamed through Den, so most setups never need this. |

### Sign-in

| Variable | Default | Required | Description |
| --- | --- | --- | --- |
| `AUTH_MODE` | `dev` | no | `oidc` checks Keycloak tokens. `dev` trusts the `X-Dev-User` header and makes everyone an admin. **Always set `oidc` outside your own computer**; see [Dev mode](../../concepts/authentication.md#dev-mode-no-keycloak). |
| `OIDC_ISSUER_URL` | none | with `oidc` | The identity provider's issuer, for example `https://auth.conservices.test/realms/conservices`. Must match the `iss` claim of the tokens exactly, and be reachable from the backend at start-up. |
| `OIDC_CLIENT_ID` | none | with `oidc` | Den's OIDC client, for example `den-spa`. |
| `OIDC_AUDIENCE` | `OIDC_CLIENT_ID` | no | The audience a token must carry. |
| `DEV_DEFAULT_USER` | `dev-admin` | no | In dev mode, the user assumed when no `X-Dev-User` header is sent. |
| `DEN_ADMIN_GROUPS` | `den-admin` | no | Comma-separated IdP groups whose members are admins. The first one is published in the role catalog. |
| `DEN_MEMBER_GROUPS` | `den-member` | no | Comma-separated IdP groups whose members may use the portal. The first one is published in the role catalog. |

!!! note "Letting every signed-in person use the portal"
    Den lets everyone who signs in use the portal when its member group list
    is empty. Because an empty variable falls back to `den-member`, the only
    way to get an empty list today is a value with no names, such as a
    single comma (`DEN_MEMBER_GROUPS=,`).

### Keycloak login branding

Optional. When `KEYCLOAK_ADMIN_URL`, `KEYCLOAK_REALM`, `KEYCLOAK_CLIENT_ID`
and `KEYCLOAK_CLIENT_SECRET` all have a value, Den pushes its brand into the
realm (see [Keycloak sync](admin-guide.md#keycloak-sync)). Otherwise the
feature is off.

| Variable | Default | Required | Description |
| --- | --- | --- | --- |
| `KEYCLOAK_ADMIN_URL` | none | for sync | How Den reaches Keycloak's API, for example `http://keycloak.conservices-identity.svc.cluster.local:8080`. Can be an internal address; Keycloak never calls Den. |
| `KEYCLOAK_REALM` | realm in `OIDC_ISSUER_URL` | no | The realm to update. By default taken from the part after `/realms/` in `OIDC_ISSUER_URL`. |
| `KEYCLOAK_CLIENT_ID` | `den-keycloak` | no | A confidential client whose service account has the `realm-management` role `manage-realm`. |
| `KEYCLOAK_CLIENT_SECRET` | none | for sync | That client's secret. |

### Operator

Optional. Without `OPERATOR_URL`, Den runs without the operator: the
Backups page says *Not set up*, and modules are added and removed without
touching databases.

| Variable | Default | Required | Description |
| --- | --- | --- | --- |
| `OPERATOR_URL` | none | no | The operator's internal address, for example `http://den-operator.conservices-den.svc.cluster.local:8080`. |
| `OPERATOR_TOKEN` | none | when `OPERATOR_URL` is set | The shared secret; must equal the operator's `OPERATOR_TOKEN`. |

### Other

| Variable | Description |
| --- | --- |
| `SSL_CERT_DIR` | Read by Go itself: a folder of extra trusted CA certificates. The example overlay sets `/etc/conservices-ca` and mounts the mkcert root there, so the backend trusts the local certificate when it talks to `https://auth.conservices.test`. The Compose stack uses `/caddy-ca`. Not needed when your identity provider has a publicly trusted certificate. |

## Migrate step

`/den-migrate` applies every pending database migration and exits with code
`0` on success and `1` on any error. It reads only `DATABASE_URL` (and
`APP_ENV` for the log format). On Kubernetes it runs as the initContainer
`migrate` of `den-backend`, from the same image, so a new version's
migrations always run before the new server starts.

```sh
/den-migrate           # apply pending migrations
/den-migrate -status   # list migrations and whether they are applied
```

## Frontend build settings

These are Docker build arguments of `infra/Dockerfile.frontend` (or
environment variables for `npm run dev` / `npm run build`). They are baked
into the image and **cannot** be changed with a ConfigMap. The published
`den-frontend` image is built with `VITE_AUTH_MODE=oidc`,
`VITE_OIDC_AUTHORITY=https://auth.conservices.test/realms/conservices` and
`VITE_OIDC_CLIENT_ID=den-spa`, which fits the example installation only. For
your own domain, build and push your own image and point the overlay's
`images:` entry at it:

```sh
docker build -f infra/Dockerfile.frontend \
  --build-arg VITE_AUTH_MODE=oidc \
  --build-arg VITE_OIDC_AUTHORITY=https://login.example.org/realms/conservices \
  --build-arg VITE_OIDC_CLIENT_ID=den-spa \
  --build-arg DEN_VERSION=1.0.0-1 \
  -t registry.example.org/den-frontend:1.0.0-1 .
```

The nginx configuration baked into the image is not used on Kubernetes: the
manifests mount their own from the `den-frontend-nginx` ConfigMap, which
listens on port 8080 and proxies `/api/` to
`den-backend.conservices-den.svc.cluster.local:8080`.

| Variable | Default | Description |
| --- | --- | --- |
| `VITE_AUTH_MODE` | `dev` | `oidc` or `dev`. Must match the backend's `AUTH_MODE`. |
| `VITE_OIDC_AUTHORITY` | none | The issuer URL, for example `https://auth.conservices.test/realms/conservices`. Required with `oidc`; the image build fails without it. |
| `VITE_OIDC_CLIENT_ID` | none | The OIDC client, for example `den-spa`. Required with `oidc`. |
| `VITE_OIDC_SCOPE` | `openid profile email` | Scopes to request. |
| `VITE_API_BASE_URL` | empty | Where the API lives. Leave empty when nginx serves the app and proxies `/api/` on the same address (the normal setup). For `npm run dev`, use `http://localhost:8090`. |
| `DEN_VERSION` | `dev` | Version shown on the Settings page. |
| `NGINX_CONF` | `nginx.conf` | Which nginx configuration from `infra/` to bake in. The Compose stack uses `nginx.stack.conf`, which proxies `/api/` to `den-backend:8080`. Overridden by a mounted file on Kubernetes. |

The backend image takes a `VERSION` build argument (default `dev`), shown by
`/livez` and `/api/health`.

## Operator

| Variable | Default | Required | Description |
| --- | --- | --- | --- |
| `OPERATOR_ADDR` | `:8080` | no | Listen address. Never expose it through an Ingress; the network policy only admits Den's backend. |
| `OPERATOR_TOKEN` | none | **yes** | Shared secret with the Den backend. Use a long random value. |
| `PG_ADMIN_URL` | none | **yes** | Superuser connection to the shared server's maintenance database, for example `postgres://postgres:…@postgres.conservices-data.svc.cluster.local:5432/postgres`. |
| `MODULE_DB_HOST` | host of `PG_ADMIN_URL` | no | The `host:port` written into connection URLs handed out for new databases. |
| `MANAGED_DATABASES` | `true` | no | Let Den create and drop module databases. |
| `PROTECTED_DATABASES` | `keycloak,den` | no | Databases that can never be dropped, in addition to `postgres`, `template0` and `template1`. |
| `BACKUP_ENABLED` | `true` | no | Turn backups off entirely with `false`. |
| `BACKUP_S3_ENDPOINT` | none | for backups | Backup storage endpoint. |
| `BACKUP_S3_BUCKET` | none | for backups | Backup bucket; created if missing. |
| `BACKUP_S3_ACCESS_KEY_ID` | none | for backups | Access key for the backup bucket. |
| `BACKUP_S3_SECRET_ACCESS_KEY` | none | for backups | Secret key for the backup bucket. |
| `BACKUP_S3_REGION` | `us-east-1` | no | Region of the backup storage. |
| `BACKUP_S3_USE_PATH_STYLE` | `true` | no | `false` for providers that need virtual-host style. |
| `BACKUP_AGE_RECIPIENTS` | none | for backups | Comma-separated age public keys (`age1…`) the backups are encrypted for. |
| `BACKUP_TIMEZONE` | `UTC` | no | Time zone of the daily backup hour, for example `Europe/Vienna`. |
| `FILES_S3_BUCKETS` | none | no | Comma-separated module buckets copied into every full backup. |
| `FILES_S3_ENDPOINT` | none | when `FILES_S3_BUCKETS` is set | Live file storage endpoint to copy from. |
| `FILES_S3_ACCESS_KEY_ID`, `FILES_S3_SECRET_ACCESS_KEY` | none | with buckets | Credentials for the live file storage. |
| `FILES_S3_REGION` | `us-east-1` | no | Region of the live file storage. |
| `FILES_S3_USE_PATH_STYLE` | `true` | no | As for backups. |

The backup hour and how many backups to keep are set in Den's admin console,
not here. How the operator works is explained in
[Databases, backups and restore](../../operations/databases-and-backups.md).

## Example: the base manifests

This is the `den-config` ConfigMap from `deploy/kubernetes/base/den/`,
which the example overlay uses unchanged:

```yaml
configMapGenerator:
  - name: den-config
    literals:
      - APP_ENV=production
      - APP_BASE_URL=https://den.conservices.test
      - HTTP_ADDR=:8080
      - AUTH_MODE=oidc
      - OIDC_ISSUER_URL=https://auth.conservices.test/realms/conservices
      - OIDC_CLIENT_ID=den-spa
      - OIDC_AUDIENCE=den-spa
      - DEN_ADMIN_GROUPS=den-admin
      - DEN_MEMBER_GROUPS=den-member
      - CORS_ALLOWED_ORIGINS=https://den.conservices.test
      - S3_ENDPOINT=http://minio.conservices-data.svc.cluster.local:9000
      - S3_BUCKET=den-data
      - S3_REGION=us-east-1
      - S3_USE_PATH_STYLE=true
      - KEYCLOAK_ADMIN_URL=http://keycloak.conservices-identity.svc.cluster.local:8080
      - KEYCLOAK_REALM=conservices
      - KEYCLOAK_CLIENT_ID=den-keycloak
      - OPERATOR_URL=http://den-operator.conservices-den.svc.cluster.local:8080
      - SHUTDOWN_TIMEOUT=15s
```

The example overlay fills `den-secrets` with **development-only** values
(for example `OPERATOR_TOKEN=den-operator-dev-token`). Never reuse them.

## Example: production overlay

A starting point for a real deployment with a managed database and S3,
based on `overlays/production-external-secrets`. Replace every value in
angle brackets. The secrets come from your secret manager: store the keys of
`den-secrets` and `den-operator-secrets` there and let the
`ExternalSecret`s in `external-secrets.yaml` create them (see
[Secrets](../../operations/secrets.md)).

```yaml
configMapGenerator:
  - name: den-config
    namespace: conservices-den
    behavior: merge
    literals:
      - APP_BASE_URL=https://den.example.org
      - CORS_ALLOWED_ORIGINS=https://den.example.org
      - OIDC_ISSUER_URL=https://login.example.org/realms/conservices
      - S3_ENDPOINT=https://<your-s3-endpoint>
      - S3_BUCKET=<den-bucket>
      - S3_REGION=<region>
  - name: den-operator-config
    namespace: conservices-den
    behavior: merge
    literals:
      - MODULE_DB_HOST=<db.example.org>:5432
      - BACKUP_S3_ENDPOINT=https://<your-s3-endpoint>
      - BACKUP_S3_BUCKET=<backup-bucket>
      - BACKUP_AGE_RECIPIENTS=<age1-public-key>
      - BACKUP_TIMEZONE=Europe/Vienna
      - FILES_S3_ENDPOINT=https://<your-s3-endpoint>
      - FILES_S3_BUCKETS=<den-bucket>,<stash-bucket>
```

And in your secret manager, at the path the `den-secrets` ExternalSecret
reads (`conservices/den/backend` in the example):

```text
DATABASE_URL            postgres://den:<password>@<db.example.org>:5432/den?sslmode=require
S3_ACCESS_KEY_ID        <access-key>
S3_SECRET_ACCESS_KEY    <secret-key>
KEYCLOAK_CLIENT_SECRET  <den-keycloak-client-secret>
OPERATOR_TOKEN          <long-random-secret>
```

Remember that the network policies only allow traffic to in-cluster
PostgreSQL, MinIO and Keycloak. Add egress rules for external services; see
[Network policies](../../operations/network-policies.md#external-services).
